Zymera · technical assessment

Could a language model help Zymera, and where would it fail?

Zymera studies how a robot team keeps its mission alive when one member misbehaves without being caught. A separate question came up: could a language model — a large one off-board, or a small one running on the robot — help the team coordinate, explain what it did, or build its training machinery? This is what the published evidence supports, stated plainly, scoped to our problem.

Read across the review and benchmark literature · numbers are as reported by the cited work · verdicts framed for Zymera's covert-adversary coverage/relay setting

The short answer. A language model is worth adding to this system in exactly one shape: a slow, occasional component that produces something reusable and checkable — a training reward written as code, a plan, a role assignment — which the fast controller then runs. It must never pick a robot's move each step. Two failures are settled by the evidence: a model in the per-step control loop breaks coordination (about 20% success on an 8-robot path-finding task, 0% in a maze), and a model small enough to run on the robot cannot do the multi-step reasoning that coordination or negotiation would need — that ceiling is around 2 billion parameters and does not move with better prompting. The single use that clearly beats current practice is having a capable model write the training reward as code, off-board, scored against the real mission.
The part that is Zymera's. Every review that touches robustness names the same open problem — a hidden, misbehaving insider under limited and lossy communication — and none of them study it. That is our thesis, and it is unoccupied. But there is a trap that sits right on our path: the compression that lets a model run on a robot silently destroys the two properties a covert-adversary defense leans on most — a well-calibrated sense of its own uncertainty, and stable behavior on its own rollout. A smaller model is not just a weaker version of the big one; it is a narrower, less-calibrated, less-honest one. If we ever put a model on-board, we must measure what the shrink removed, not only what it kept.

What to actually do — in order

1
Write the training reward as code, off-board, on a capable model.

Let a large model propose and revise the coverage-and-connectivity reward (and the training curriculum) as an executable function, run the real mission, and improve from the result. This is the strongest single result in the whole body of work — a method of this kind beat expert-written rewards on 83% of 29 tasks, +52% on average — and it runs entirely off the fast loop, so no small on-board model ever has to carry it. Failure mode: if the model only sees a coarse score it optimizes the wrong thing. Feed it the mission-level outcome and keep a validator that rejects any reward that breaks the rules.

2
Do not put a model in the control loop, or on the robot as a reasoner.

Per-step language control collapses coordination, and the on-board size that battery and memory allow is below the reasoning ceiling. Both are measured, not assumed. If a demo tempts you otherwise, budget-match it against a plain controller first; the apparent gains in this literature usually come from a good default, not the model.

3
Probe the covert-adversary channel — the thing no one has tested.

Communication is the coordination bottleneck: degrade or drop the channel and measure how fast success falls. That same experiment is our direct test of a hidden agent quietly corrupting messages — the micro-misbehavior-to-mission-failure link Zymera is about. Failure mode: model compression erodes the calibration this depends on — so if a small model is anywhere in the loop, co-measure what it lost.

4
If we ever explain a decision, explain a simplified stand-in and test it by intervention.

Compress the trained controller into a short, checkable decision path, have the model put that into words, and verify each explanation by removing the feature it cites and confirming the decision actually changes. A model's own after-the-fact reasoning is not trustworthy. Failure mode: the words describe the stand-in, not the network — never accept a self-report as ground truth.

1Can it help the team coordinate?

A language model can turn a goal into a persistent plan or role assignment that a fast controller then executes, and a small model that is constrained to the task can beat a larger one that is not. It fails the moment it is queried every control step, and it has never been shown to coordinate more than about ten robots. The recurring lesson is that communication is the bottleneck — which is exactly the surface Zymera attacks.

Consensus: coordination has to be built in — through roles, protocols, and explicit capability — not expected to appear on its own from letting models talk. Dropping the channel collapses success, which doubles as our probe for a corrupted-message attack.

2Can it explain what the policy did?

The reliable recipe is not to have the model narrate the raw network. It is to first compress the trained controller into a simple, checkable form — a short decision path or small tree — and have the model put that into words. This roughly halves made-up explanations, and it helps small models the most. A model's own stated reasoning is not faithful: reorder the choices and the answer flips, while the explanation never mentions the reorder.

3Can it build or tune the training machinery?

It helps when it writes code that an external check scores — a reward function, a heuristic — and iterates on the result. It does not help as a numeric knob-tuner: as the number of knobs grows it degrades fast and loses to standard optimizers. And a small on-board model cannot do either — it falls below the threshold for self-improvement.

Consensus: a model beats classic methods only when it writes code that a real run scores, and loses everywhere the problem is numeric or high-dimensional — which is where a training sweep lives. So: design the reward as code off-board against the real coverage-and-connectivity run; use a standard optimizer for the numeric grind.

The small on-board model wall

This is where the on-robot version lives or dies. The measurements are sharp.

What we would needWhere a small model is fineWhere it hits the wall
Reasoning by model sizeClassifying, retrieving, drafting, short factual answers are solid at 1–3 billion parameters and ship on phones todayMulti-step reasoning collapses below ~2 billion — the exact ability a coordinator or negotiator needs is the first to go
What matters more than sizeData quality beats parameter count — a well-trained 1.5B model beats several 3B onesThere is no size-vs-ability rule for on-device models; the usual scaling law does not apply
Compressing a big model downInstruction-following, step-by-step format, tool use, and domain skill transfer; a compressed model can even beat its teacher on narrow tasksIt cannot create reasoning that was not there at the small size — no shrinking past the reasoning wall
What compression quietly costs—Calibration, stable behavior on its own rollout, grounding, safety, output variety — the shrunk model looks smaller but is really narrower and less honest
Energy4-bit weights are near-free above 1B; the standard efficient building blocks are mature~700 words per phone charge; an always-on model on every robot is not affordable

Reading: the energy budget does not merely allow the slow-occasional-model design — it forces it. But the small model cannot be the team's reasoner; it can only emit structured artifacts that an external check verifies (the model proposes, a connectivity check or planner confirms, and the loop repeats on failure). Full training on the robot is off the table — only light adaptation fits on-board.

Cooperation, competition, and a hidden adversary

The part closest to Zymera's frame — a team that shares one goal, sees only part of the world, and may contain a member trying not to be caught.

Headline. When language models are placed in game settings, they are studied by watching behavior, not by solving the game. Three things that behavior shows bear directly on us: (1) models have no fixed stance — cooperative by default in simple fair-split games, but this is a thin training habit, not strategy; (2) more reasoning ability makes them defect more — better models free-ride harder in shared-resource games, so a capable hidden defector is the expected outcome, not a fluke; (3) in games with a hidden traitor, models notice the betrayal but fail to adapt as a team, and they produce deception better than they catch it — the defender is the weaker side. Where genuine mix-of-cooperate-and-compete skill appears (the game Diplomacy), it came from bolting a proper game-solver onto the model, not from the language.

Is any of this set up as Zymera's kind of problem?

Almost none. Zymera's frame is a specific formal object — a team that shares one reward and each sees only part of the world (a cooperative partially-observed team problem), analyzed as a contest against a member who is trying to stay undetected (a partially-observed stochastic game with a stealth-limited insider). The language-model game literature approaches this from separate sides that never meet:

Line of workWhat it hasWhat it is missing
CICERO (Diplomacy)A real strategy solver plus self-play on a mixed cooperate/compete gameThe solver, not the language model, does the strategy; specific to one game
Hidden-traitor + comms (Byzantine Cheap Talk)Our exact situation — a covert defector, a communication graph, local detectionOnly watched, not formalized: no measure of how hard the defector is to detect, no notion of a smallest damaging group
Byzantine-robust LLM teamsOur exact defense — a graph rule that filters out bad neighborsTreats the bad agent as a random fault, not a deliberate hider optimizing to evade
Mixed-motive benchmarks (Melting Pot lineage)A clean partially-observed team setting to test inNo inside adversary, and no measure of whether the mission survives

The gap, precisely: no one has put a language-model team inside a shared-reward, partial-view mission with a hidden member who is optimizing to stay undetected, scored by whether the mission survives. The pieces exist apart; the combination — which is Zymera — is empty. The closest prior work to cite is the hidden-traitor-plus-communication study (informal) and the graph-filter defense (treats the adversary as a fault, not a strategist).
